# 自动预测作业恢复运行手册（2026-08-21）

## 1. 文档定位

本手册是销售预测正式环境自动作业的恢复、发布、验证、回滚和连续运行验收依据。

适用环境：

- 项目目录：`/opt/forecasting_app/current`
- Python：`/opt/forecasting_app/venv/bin/python`
- 环境文件：`/etc/forecasting_app.env`
- 平台状态库：`/opt/forecasting_app/current/data/platform_state.db`
- 共享执行锁：`/run/lock/forecast-execution.lock`
- API 服务：`forecast-dashboard-v2.service`
- 周作业：`forecast-weekly.service`
- 周定时器：`forecast-weekly.timer`
- 固定计划：每周一 `01:00`，Linux 主机时区必须为 `Asia/Shanghai`

本手册不记录任何真实密码、Token、数据库连接串或其他凭据。禁止执行 `cat /etc/forecasting_app.env`、`env`、`printenv` 等可能把凭据写入终端或采证文件的命令。

- `forecast-dashboard-v2.service` 为 `active/running/enabled`。

- 同日 `02:38` 又产生一个运行，停在 `3/146`，最后更新时间为 `04:16`，但状态仍为 `running`。

结论：基础服务在线，但自动执行链路异常。恢复重点不是单纯重启 API，而是消除双调度、清理孤儿运行状态、统一执行锁并重新建立周作业验收证据。

## 3. 权威边界与红线

### 3.1 systemd 是唯一调度权威

- 正式自动触发只允许来自 `forecast-weekly.timer`。
- `forecast-dashboard-v2.service` 必须设置 `FORECAST_INTERNAL_SCHEDULER_ENABLED=false`。
- 不得把 API 进程内 scheduler、页面“每周作业时间”或其他 cron 作为第二个正式调度源。
- 页面中的计划时间只能作为展示信息，不能替代 systemd timer 配置。
- 调整计划时间必须修改、评审并发布 `deploy/systemd/forecast-weekly.timer`，再执行 `systemd-analyze verify`。

### 3.2 所有执行入口共用同一把锁

以下入口必须统一使用 `/run/lock/forecast-execution.lock`：

- `forecast-weekly.service`
- 监督全量执行
- 单 SPU smoke
- Dashboard/API 发起的临时执行
- 孤儿状态恢复脚本

锁被占用时必须停止新执行并查明持有者。不得通过删除锁文件、换一个锁路径或去掉 `--lock-file` 绕过互斥。

### 3.3 timer 冻结门禁

从恢复开始到“首次全量”通过之前，`forecast-weekly.timer` 必须保持 `disabled/inactive`。只有满足以下条件才允许重新启用：

1. 部署与 systemd 校验完成。
2. 孤儿运行状态已恢复，状态库完整性检查通过。
3. Dashboard 内部 scheduler 已关闭。
4. 单 SPU、结果不落库 smoke 通过。
5. 监督全量通过。

## 4. 三层状态定义

| 状态 | 必须满足的条件 | 允许结论 |
|---|---|---|
| 部署完成 | 代码和 unit 已部署；`systemd-analyze verify` 通过；内部 scheduler 关闭；共享锁一致；Dashboard 健康；单 SPU no-persist smoke 通过；timer 仍冻结 | 只能说“部署完成”，不能说自动作业已恢复稳定 |
| 首次全量 | 在 timer 冻结状态下，人工监督 `forecast-weekly.service` 完成一次全量；只产生一个运行；`processed_count=total_count`；无 SQLite 锁冲突；失败 SPU 已审查 | 可以重新启用 timer，但不能说连续运行已验收 |
| 连续两周验收 | 连续两个周一 01:00 各自动触发且只触发一次；两次均完成；没有重复运行、孤儿状态或数据库锁冲突；证据完整 | 可以说“自动预测恢复稳定并通过连续两周验收” |

任何一级未通过，都不得越级声明后一级完成。

## 5. 恢复前准备

### 5.1 设置本次操作变量

在同一个受控 Shell 会话中执行：

```bash
set -euo pipefail

PROJECT_ROOT=/opt/forecasting_app/current
PYTHON_BIN=/opt/forecasting_app/venv/bin/python
STATE_DB=/opt/forecasting_app/current/data/platform_state.db
EXEC_LOCK=/run/lock/forecast-execution.lock
RUNBOOK_TS=$(date -u +%Y%m%dT%H%M%SZ)
BACKUP_ROOT=/opt/forecasting_app/backups/auto-recovery-${RUNBOOK_TS}-$$

cd "$PROJECT_ROOT"
sudo install -d -m 0700 /opt/forecasting_app/backups
if sudo test ! -e "$BACKUP_ROOT" && sudo test ! -L "$BACKUP_ROOT"; then
  :
else
  echo 'backup path already exists or cannot be checked with root privileges' >&2
  exit 1
fi
sudo mkdir "$BACKUP_ROOT"
sudo chmod 0700 "$BACKUP_ROOT"
```

### 5.2 记录变更前基线

```bash
date -Is
timedatectl status
git status --short
git rev-parse HEAD
sudo systemctl is-enabled forecast-dashboard-v2.service || true
sudo systemctl is-active forecast-dashboard-v2.service || true
sudo systemctl is-enabled forecast-weekly.timer || true
sudo systemctl is-active forecast-weekly.timer || true
sudo systemctl status forecast-weekly.service --no-pager || true
sudo systemctl list-timers forecast-weekly.timer --all --no-pager
curl -fsS http://127.0.0.1:8000/api/health
curl -fsS http://127.0.0.1:8000/api/linux-ops | "$PYTHON_BIN" -m json.tool
```

通过标准：

- `timedatectl` 显示 `Asia/Shanghai`；否则先修正时区并重新核对下一次触发时间。
- 生产工作树必须干净；存在未确认修改时停止发布。
- 记录当前 commit、服务状态、timer 的 `LAST/NEXT` 和当前运行状态。

### 5.3 备份配置和部署信息

环境文件只能复制到权限为 `0700` 的备份目录，禁止显示内容。

```bash
sudo cp -a /etc/systemd/system/forecast-dashboard-v2.service "$BACKUP_ROOT/"
sudo cp -a /etc/systemd/system/forecast-weekly.service "$BACKUP_ROOT/"
sudo cp -a /etc/systemd/system/forecast-weekly.timer "$BACKUP_ROOT/"
sudo cp -a /etc/forecasting_app.env "$BACKUP_ROOT/forecasting_app.env"
sudo chmod 0600 "$BACKUP_ROOT/forecasting_app.env"

git rev-parse HEAD | sudo tee "$BACKUP_ROOT/app_commit.txt" >/dev/null
sudo systemctl status forecast-dashboard-v2.service --no-pager \
  | sudo tee "$BACKUP_ROOT/dashboard-status.before.txt" >/dev/null || true
sudo systemctl status forecast-weekly.timer --no-pager \
  | sudo tee "$BACKUP_ROOT/timer-status.before.txt" >/dev/null || true
sudo systemctl list-timers forecast-weekly.timer --all --no-pager \
  | sudo tee "$BACKUP_ROOT/timers.before.txt" >/dev/null
```

平台状态库不要在 Dashboard 仍写入时直接用 `cp` 复制。后续由恢复脚本在共享锁内执行 SQLite 在线备份和完整性校验。

## 6. 冻结 timer 与建立 Dashboard 写窗口

### 6.1 冻结自动入口

```bash
sudo systemctl disable --now forecast-weekly.timer
sudo systemctl stop forecast-weekly.service
sudo systemctl is-enabled forecast-weekly.timer || true
sudo systemctl is-active forecast-weekly.timer || true
sudo systemctl is-active forecast-weekly.service || true
```

通过标准：timer 为 `disabled/inactive`，weekly service 为 `inactive`。

### 6.2 建立状态库写窗口

涉及状态库恢复、数据库文件恢复或 schema 迁移时，必须先停止 Dashboard，阻断 API 写入：

```bash
sudo systemctl stop forecast-dashboard-v2.service
sudo systemctl is-active forecast-dashboard-v2.service || true
pgrep -af 'run_forecast_job.py|src.api.app:app' || true
sudo /usr/bin/flock -n "$EXEC_LOCK" -c 'echo execution-lock-free'
```

如果仍有预测进程或锁不可获得：

1. 不得继续恢复或发布。
2. 先采集进程、service 和日志证据。
3. 只通过对应 systemd unit 停止进程。
4. 再次确认锁可获得。

锁文件本身存在不代表锁被占用，不得删除它。

## 7. 发布与 systemd 校验

### 7.1 发布批准版本

将批准的发布引用写入变量；占位值未替换时命令会安全退出：

```bash
APPROVED_RELEASE_REF=REPLACE_WITH_APPROVED_RELEASE_REF
test "$APPROVED_RELEASE_REF" != REPLACE_WITH_APPROVED_RELEASE_REF || {
  echo 'APPROVED_RELEASE_REF is not set'
  exit 1
}

cd "$PROJECT_ROOT"
test -z "$(git status --porcelain)" || {
  echo 'production worktree is not clean'
  exit 1
}
git fetch origin
git checkout "$APPROVED_RELEASE_REF"
git rev-parse HEAD
```

确认输出的 commit 与审批记录完全一致后才能继续。

### 7.2 安装并验证 unit

```bash
cd "$PROJECT_ROOT"
sudo cp deploy/systemd/forecast-dashboard-v2.service /etc/systemd/system/
sudo cp deploy/systemd/forecast-weekly.service /etc/systemd/system/
sudo cp deploy/systemd/forecast-weekly.timer /etc/systemd/system/

sudo systemd-analyze verify /etc/systemd/system/forecast-dashboard-v2.service
sudo systemd-analyze verify /etc/systemd/system/forecast-weekly.service
sudo systemd-analyze verify /etc/systemd/system/forecast-weekly.timer

grep -F 'Environment=FORECAST_INTERNAL_SCHEDULER_ENABLED=false' \
  /etc/systemd/system/forecast-dashboard-v2.service
if sudo grep -Eiq '^FORECAST_INTERNAL_SCHEDULER_ENABLED=(1|true|yes|on)$' \
  /etc/forecasting_app.env; then
  echo 'internal scheduler is enabled in the environment file'
  exit 1
fi
grep -F '/run/lock/forecast-execution.lock' \
  /etc/systemd/system/forecast-weekly.service
grep -F 'OnCalendar=Mon *-*-* 01:00:00' \
  /etc/systemd/system/forecast-weekly.timer

sudo systemctl daemon-reload
sudo systemctl disable --now forecast-weekly.timer
```

任何一个 verify 或 grep 失败都判定“部署未完成”。timer 必须继续冻结。

## 8. 状态库备份与孤儿运行恢复

在 Dashboard 已停止、timer 已冻结、weekly service 已停止的前提下执行：

```bash
cd "$PROJECT_ROOT"
if sudo test ! -e "$BACKUP_ROOT/platform_state.pre-recovery.db" \
  && sudo test ! -L "$BACKUP_ROOT/platform_state.pre-recovery.db"; then
  :
else
  echo 'recovery backup path already exists or cannot be checked; create a new BACKUP_ROOT' >&2
  exit 1
fi
sudo "$PYTHON_BIN" scripts/recover_forecast_state.py \
  --platform-db "$STATE_DB" \
  --backup-path "$BACKUP_ROOT/platform_state.pre-recovery.db" \
  --lock-file "$EXEC_LOCK" \
  --reason 'Approved recovery closed orphaned active runs before controlled validation.' \
  | sudo tee "$BACKUP_ROOT/state-recovery.json"
```

恢复脚本必须同时完成：

- 在共享锁内创建不覆盖已有文件的 SQLite 备份。
- 恢复前、备份文件、恢复后的 `integrity_check` 均为 `ok`。
- 将孤儿 `queued/running/stopping` 记录关闭为终态并留下审计原因。
- 恢复后 active run 数量为 `0`。
- active-run 唯一约束可用。

任一条件不满足时停止，不得启动 smoke 或全量。

```bash
sudo systemctl reset-failed forecast-dashboard-v2.service
sudo systemctl enable --now forecast-dashboard-v2.service
sudo systemctl status forecast-dashboard-v2.service --no-pager
curl -fsS http://127.0.0.1:8000/api/health

  | sudo tee "$BACKUP_ROOT/linux-ops.after-recovery.json"
sudo systemctl is-enabled forecast-weekly.timer || true
sudo systemctl is-active forecast-weekly.timer || true
```

通过标准：

- Dashboard 为 `active/running/enabled`。
- `/api/health` 返回健康。
- `/api/linux-ops` 显示 `scheduler_authority=systemd`。
- `internal_scheduler_enabled=false`。
- 没有 active run。
- timer 仍为 `disabled/inactive`。

## 10. 单 SPU、结果不落库 smoke

smoke 使用正式环境变量文件，但不得输出其内容。`--max-spus 1` 只取一个符合正式筛选条件的 SPU；`--no-persist-results` 禁止写预测结果表，但仍保留平台运行审计记录。

```bash
cd "$PROJECT_ROOT"
sudo systemd-run \
  --unit=forecast-recovery-smoke \
  --wait \
  --collect \
  --pipe \
  --property=WorkingDirectory="$PROJECT_ROOT" \
  --property=EnvironmentFile=/etc/forecasting_app.env \
  "$PYTHON_BIN" scripts/run_forecast_job.py \
  --mode smart \
  --selection-type all \
  --max-spus 1 \
  --trigger-source smoke \
  --no-persist-results \
  --lock-file "$EXEC_LOCK" \
  2>&1 | sudo tee "$BACKUP_ROOT/smoke.log"
```

smoke 通过标准：

- 获得并最终释放 `/run/lock/forecast-execution.lock`。
- 只创建一个 smoke run。
- 最终状态为 `completed`，`processed_count=total_count=1`。
- 日志明确显示结果持久化已关闭。
- 无 `database is locked`、重复运行、孤儿 active run。
- timer 仍为 `disabled/inactive`。

smoke 未通过时，状态保持“部署未完成”，进入第 15 节失败重置周期。

## 11. 监督全量

单 SPU smoke 通过后，保持 timer 冻结，使用正式 `forecast-weekly.service` 人工发起一次全量：

```bash
sudo systemctl reset-failed forecast-weekly.service
sudo systemctl start --no-block forecast-weekly.service
sudo systemctl status forecast-weekly.service --no-pager
sudo tail -F /var/log/forecast-weekly.log
```

另开只读窗口持续检查：

```bash
curl -fsS http://127.0.0.1:8000/api/linux-ops \
  | /opt/forecasting_app/venv/bin/python -m json.tool
curl -fsS 'http://127.0.0.1:8000/api/forecast-jobs?limit=10' \
  | /opt/forecasting_app/venv/bin/python -m json.tool
sudo systemctl status forecast-weekly.service --no-pager
```

全量完成后采证：

```bash
sudo systemctl status forecast-weekly.service --no-pager \
  | sudo tee "$BACKUP_ROOT/weekly-full.status.txt" >/dev/null || true
sudo tail -n 500 /var/log/forecast-weekly.log \
  | sudo tee "$BACKUP_ROOT/weekly-full.log" >/dev/null
curl -fsS http://127.0.0.1:8000/api/linux-ops \
  | "$PYTHON_BIN" -m json.tool \
  | sudo tee "$BACKUP_ROOT/weekly-full.linux-ops.json" >/dev/null
curl -fsS 'http://127.0.0.1:8000/api/forecast-jobs?limit=10' \
  | "$PYTHON_BIN" -m json.tool \
  | sudo tee "$BACKUP_ROOT/weekly-full.runs.json" >/dev/null
```

首次全量通过标准：

- 本次只产生一个 run。
- 运行达到终态 `completed`。
- `processed_count=total_count`；总数按当次正式筛选结果认定，不硬编码历史的 `145` 或 `146`。
- `success_count`、失败明细和结果落库情况已人工审查；存在失败 SPU 时必须有可接受结论。
- 没有 `SQLite database is locked`、执行锁冲突或重复 schedule slot。
- 执行结束后 `forecast-weekly.service` 为 `inactive/dead (success)`，这是 oneshot 正常空闲状态。
- 没有残留 `queued/running/stopping` 记录。

## 12. 启用 timer

只有首次全量通过后才能执行：

```bash
sudo systemctl reset-failed forecast-weekly.service
sudo systemctl enable --now forecast-weekly.timer
sudo systemctl is-enabled forecast-weekly.timer
sudo systemctl is-active forecast-weekly.timer
sudo systemctl list-timers forecast-weekly.timer --all --no-pager
systemd-analyze calendar 'Mon *-*-* 01:00:00'
```

通过标准：

- timer 为 `enabled/active/waiting`。
- `NEXT` 是最近的周一 `01:00`，并与 `Asia/Shanghai` 时区一致。
- weekly service 在等待期间为 `inactive/dead` 属正常状态。

此时状态只能标记为“首次全量通过，timer 已恢复”，还不能标记“连续两周验收通过”。

## 13. 连续两周验收与采证

### 13.1 每周验收标准

连续两个自然周的周一均须满足：

1. `forecast-weekly.timer` 在 `01:00` 触发一次且仅一次。
2. 对应 run 的 `trigger_source=schedule`，同一周不存在第二个 schedule run。
3. run 最终为 `completed`，`processed_count=total_count`。
4. 没有 `SQLite database is locked`、共享锁绕过、重复 slot 或孤儿 active run。
5. Dashboard 全程可读；`/api/health` 正常。
6. timer 的 `LAST/NEXT` 与本周、下周计划一致。
7. 失败 SPU 数量和失败原因经过业务与算法负责人审查。

### 13.2 每周采证命令

在作业启动后和作业完成后分别采集一次。每周使用新的证据目录：

```bash
EVIDENCE_TS=$(date -u +%Y%m%dT%H%M%SZ)
EVIDENCE_ROOT=/opt/forecasting_app/evidence/weekly-${EVIDENCE_TS}-$$
sudo install -d -m 0750 /opt/forecasting_app/evidence
if sudo test ! -e "$EVIDENCE_ROOT" && sudo test ! -L "$EVIDENCE_ROOT"; then
  :
else
  echo 'weekly evidence path already exists or cannot be checked with root privileges' >&2
  exit 1
fi
sudo mkdir "$EVIDENCE_ROOT"
sudo chmod 0750 "$EVIDENCE_ROOT"

date -Is | sudo tee "$EVIDENCE_ROOT/captured-at.txt" >/dev/null
git -C /opt/forecasting_app/current rev-parse HEAD \
  | sudo tee "$EVIDENCE_ROOT/app-commit.txt" >/dev/null
sudo systemctl status forecast-dashboard-v2.service --no-pager \
  | sudo tee "$EVIDENCE_ROOT/dashboard.status.txt" >/dev/null || true
sudo systemctl status forecast-weekly.timer --no-pager \
  | sudo tee "$EVIDENCE_ROOT/timer.status.txt" >/dev/null || true
sudo systemctl status forecast-weekly.service --no-pager \
  | sudo tee "$EVIDENCE_ROOT/weekly.status.txt" >/dev/null || true
sudo systemctl list-timers forecast-weekly.timer --all --no-pager \

sudo journalctl -u forecast-weekly.timer --since 'today 00:50:00' --no-pager \

sudo journalctl -u forecast-weekly.service --since 'today 00:50:00' --no-pager \
  | sudo tee "$EVIDENCE_ROOT/weekly.journal.txt" >/dev/null
sudo tail -n 1000 /var/log/forecast-weekly.log \
  | sudo tee "$EVIDENCE_ROOT/weekly.log.txt" >/dev/null
curl -fsS http://127.0.0.1:8000/api/health \
  | sudo tee "$EVIDENCE_ROOT/api-health.json" >/dev/null
curl -fsS http://127.0.0.1:8000/api/linux-ops \
  | /opt/forecasting_app/venv/bin/python -m json.tool \
  | sudo tee "$EVIDENCE_ROOT/linux-ops.json" >/dev/null
curl -fsS 'http://127.0.0.1:8000/api/forecast-jobs?limit=10' \
  | /opt/forecasting_app/venv/bin/python -m json.tool \

```

连续两周证据必须标注“第 1 周”与“第 2 周”，并由执行人和独立验收人分别签字或留审批记录。

## 14. 回滚

### 14.1 回滚触发条件

- Dashboard 无法启动或健康检查失败。
- systemd unit 校验失败且不能在窗口内修复。
- smoke 或首次全量出现新增阻断性问题。
- 状态库迁移导致不可恢复的不兼容。
- 新版本产生重复运行、锁绕过或结果写入风险。

### 14.2 回滚步骤

先把 `BACKUP_ROOT` 明确设置为本次批准使用的绝对备份目录，并确认目录存在；不得依赖已经结束的旧 Shell 会话变量：

```bash
set -euo pipefail

rollback_gate_failed() {
  echo "ROLLBACK_GATE_FAILED: $1" >&2
  exit 1
}

require_fixed_text() {
  local expected_text=$1
  local target_file=$2
  if ! sudo grep -Fq -- "$expected_text" "$target_file"; then
    rollback_gate_failed "missing required setting in $target_file"
  fi
}

BACKUP_ROOT=/opt/forecasting_app/backups/REPLACE_WITH_APPROVED_BACKUP_DIRECTORY
if sudo test -L "$BACKUP_ROOT" || ! sudo test -d "$BACKUP_ROOT"; then
  rollback_gate_failed 'approved backup directory is missing or is a symlink'
fi
```

### 14.3 SQLite 状态库安全恢复

状态库恢复属于最后手段，必须由审批人明确指定 `APPROVED_DB_BACKUP`。严禁用 `cp`、`install`、重定向或其他方式直接覆盖 live `platform_state.db`。

恢复期间必须满足：

- timer、Dashboard、weekly service 全部停止。
- 从当前 live 库备份开始，到恢复、审计闭合孤儿运行和最终完整性检查结束，全程持有 `/run/lock/forecast-execution.lock`。
- 持锁后先在 live 库成功执行 WAL checkpoint、切换 `journal_mode=DELETE`、`integrity_check` 和 `fsync`，证明当前库已经自包含。
- 再通过 SQLite Backup API 把当前自包含 live 库备份到全新证据路径，并对证据备份执行 `integrity_check`。
- 审批备份恢复到 live 库同目录的 stage DB；schema 检查、孤儿审计闭合、唯一索引、`journal_mode=DELETE`、完整性检查和 `fsync` 全部只在 stage 完成，live 保持不变。
- stage 全部通过后，才安全归档并移除已 checkpoint 的 live `-wal/-shm/-journal`，再用 `os.replace` 原子发布。
- 发布后只做 immutable 完整性检查；若发布或发布后检查失败，自动使用本次 current evidence 构造 compensation 临时库并原子恢复 live。
- 任一错误发生后，三个 unit 保持停止，不得启动 Dashboard 或 timer。

```bash
def fail(message):
    raise RuntimeError(message)


def require_absolute(raw, label):
    path = Path(raw)
    if not path.is_absolute():
        fail(f'{label} must be absolute: {path}')
    return path


def require_under(path, root, label):

        path.relative_to(root)
    except ValueError as exc:
        raise RuntimeError(f'{label} must stay under {root}: {path}') from exc


def ro_uri(path, immutable=False):
    suffix = '?mode=ro&immutable=1' if immutable else '?mode=ro'

def integrity(connection, label):
    rows = [str(row[0]) for row in connection.execute('PRAGMA integrity_check')]
    if rows != ['ok']:
        fail(f'{label} integrity_check failed: {rows}')
    return 'ok'


def fsync_file(path):
    with open(path, 'r+b') as handle:

def fsync_dir(path):
    descriptor = os.open(path, os.O_RDONLY | getattr(os, 'O_DIRECTORY', 0))
    try:
        os.fsync(descriptor)
    finally:
        os.close(descriptor)


def sqlite_backup(source, destination, immutable_source=False):
    if destination.exists() or destination.is_symlink():
        fail(f'backup path already exists: {destination}')
    try:
        with closing(sqlite3.connect(ro_uri(source, immutable_source), uri=True, timeout=30)) as src:
            source_ok = integrity(src, f'source {source}')
            with closing(sqlite3.connect(str(destination), timeout=30)) as dst:
                src.backup(dst)
                dst.execute('PRAGMA journal_mode=DELETE')
                destination_ok = integrity(dst, f'backup {destination}')
                dst.commit()

        fsync_dir(destination.parent)

    except BaseException:
        try:

        except FileNotFoundError:
            pass
        raise


def copy_sidecar_exclusive(source, destination):
    if destination.exists() or destination.is_symlink():
        fail(f'sidecar evidence path already exists: {destination}')
    input_fd = os.open(source, os.O_RDONLY | getattr(os, 'O_NOFOLLOW', 0))
    source_stat = os.fstat(input_fd)
    if not stat.S_ISREG(source_stat.st_mode):
        os.close(input_fd)
        fail(f'sidecar is not a regular file: {source}')
    try:
        output_fd = os.open(destination, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
    except BaseException:
        os.close(input_fd)
        raise
    try:
        with os.fdopen(input_fd, 'rb') as input_handle, os.fdopen(output_fd, 'wb') as output_handle:
            shutil.copyfileobj(input_handle, output_handle)
            output_handle.flush()
            os.fsync(output_handle.fileno())
    except BaseException:
        try:
            destination.unlink()
        except FileNotFoundError:
            pass
        raise
    if destination.stat().st_size != source_stat.st_size:
        fail(f'sidecar evidence size mismatch: {source}')


def archive_and_remove_sidecars(live, evidence, phase):
    archived = []
    for suffix in ('-wal', '-shm', '-journal'):
        sidecar = Path(str(live) + suffix)
        if not sidecar.exists() and not sidecar.is_symlink():
            continue
        if sidecar.is_symlink():
            fail(f'sidecar must not be a symlink: {sidecar}')
        destination = evidence / f'platform_state.{phase}{suffix}'
        copy_sidecar_exclusive(sidecar, destination)
        sidecar.unlink()
        archived.append(str(destination))
    fsync_dir(live.parent)
    fsync_dir(evidence)
    return archived


def immutable_integrity(path, label):
    with closing(sqlite3.connect(ro_uri(path, immutable=True), uri=True, timeout=30)) as connection:
        return integrity(connection, label)


def checkpoint_live(live):
    connection = sqlite3.connect(str(live), timeout=30, isolation_level=None)
    try:
        integrity_before = integrity(connection, 'live database before checkpoint')
        checkpoint = connection.execute('PRAGMA wal_checkpoint(TRUNCATE)').fetchone()
        if checkpoint is not None and int(checkpoint[0]) != 0:
            fail(f'live WAL checkpoint remained busy: {checkpoint}')
        journal_mode = str(connection.execute('PRAGMA journal_mode=DELETE').fetchone()[0]).lower()
        if journal_mode != 'delete':
            fail(f'live database journal_mode is {journal_mode}, expected delete')
        integrity_after = integrity(connection, 'live database after checkpoint')
    finally:
        connection.close()
    fsync_file(live)
    fsync_dir(live.parent)
    immutable_after = immutable_integrity(live, 'self-contained live database')
    return {
        'integrity_before_checkpoint': integrity_before,
        'integrity_after_checkpoint': integrity_after,
        'immutable_integrity_after_checkpoint': immutable_after,
        'checkpoint_result': list(checkpoint) if checkpoint is not None else None,
        'journal_mode': journal_mode,
    }
```

## 15. 失败重置周期

### 15.1 触发条件

以下任一情况立即进入失败重置周期：

- timer 触发后出现两个或更多 schedule run。
- `database is locked` 或共享锁异常。
- run 长时间无进度且仍为 active。
- weekly service 为 `failed`。
- 运行未达到 `processed_count=total_count`。
- Dashboard 内部 scheduler 被开启。
- 任何人工绕过共享锁的执行。

### 15.2 固定顺序

1. 立即 `disable --now forecast-weekly.timer`。
2. 采集 timer、service、进程、API 运行记录和日志证据。
3. 停止 weekly service；需要修复状态库时再停止 Dashboard，建立写窗口。
4. 使用 `scripts/recover_forecast_state.py` 在共享锁内备份并关闭孤儿运行。
5. 修复根因；不得先无脑重试。
6. 重新执行 systemd verify 和单 SPU no-persist smoke。
7. 根因已修复且 smoke 通过后，执行 `systemctl reset-failed forecast-weekly.service`，只用于解除失败计数并允许监督全量。
8. 执行一次监督全量。
9. 全量通过后再次确认失败状态已清除，再重新启用 timer。
10. 连续两周验收计数清零，从下一个成功周一重新计算第 1 周。

常用命令：

```bash
sudo systemctl disable --now forecast-weekly.timer
sudo systemctl stop forecast-weekly.service
sudo systemctl status forecast-weekly.service --no-pager || true
sudo journalctl -u forecast-weekly.timer -n 200 --no-pager
sudo journalctl -u forecast-weekly.service -n 500 --no-pager
sudo tail -n 1000 /var/log/forecast-weekly.log
curl -fsS http://127.0.0.1:8000/api/linux-ops \
  | /opt/forecasting_app/venv/bin/python -m json.tool
```

`systemctl reset-failed` 只清除 systemd 失败计数，不会修复 SQLite 中的孤儿运行，也不会消除双调度源。不得把它当作恢复完成。
